## 原项目核心理解

眺览 TillGlance 是一个 Chrome 扩展。它的核心不是总结文章，而是把网页内容清洗成更适合阅读的版式，并用高亮标出视觉落点，引导用户更快阅读。

本地扩展代码主要做四件事：

1. 从网页或用户选中文本中提取正文。
2. 用 Readability 逻辑整理文章，并给可高亮段落编号，例如 `rr0`、`rr1`。
3. 将段落文本整理成 `contentDict`，请求 `nlphl` 高亮服务。
4. 收到每段的高亮位置数组后，在页面中把对应字符包成高亮元素。

已确认：本地包里能看到高亮渲染和正文抽取逻辑，但真正决定“哪些字应该高亮”的核心 NLP/眼动预测逻辑在远程 `nlphl` 服务侧，不在本地 bundle 里。

## 当前产品假设

高亮本身能提高阅读效率，这一点先沿用眺览产品已经验证过的方向。

本次二次开发真正要验证的是：

> 大模型能不能根据语义、词边界、句子结构和阅读节奏，选出接近原眺览算法的高亮位置。

因此第一阶段不直接验证“是否读得更快”，而是把原眺览算法输出当作老师标签，验证大模型能否模仿它。

## 初步评价标准

先把“好的高亮位置”定义为：

- 和原眺览算法输出接近；
- 允许前后偏差 1 到 2 个汉字；
- 高亮密度不能明显高于或低于原算法；
- 视觉上不能变成“到处都亮”，否则会失去引导效果。

## 理论锚点

- 阅读不是眼睛平滑扫过文字，而是由注视和眼跳组成。
- 眼动位置会受到词频、词长、语义预判、阅读难度等因素影响。
- 中文阅读没有自然空格，词边界和语义透明度会影响眼跳目标选择。
- 粗暴高亮不一定有效，例如固定把每个词前半部分加粗的方式在研究中结果并不稳定。

这说明大模型方向有合理性，但不能只靠“懂语义”来证明有效，必须做模仿实验。

## 最小验证实验

第一版实验可以这样做：

1. 选取 20 到 50 篇中文文章，覆盖新闻、科普、评论、长文。
2. 用原眺览算法生成每篇文章的高亮位置，保存为基准数据。
3. 把同样段落发给大模型，要求输出相同格式的高亮位置数组。
4. 计算大模型输出与基准高亮的相似度。
5. 人工抽样看视觉效果，判断是否像阅读轨道，而不是随机强调。

建议先用三个指标：

- 位置命中率：高亮起点是否落在原算法附近。
- 覆盖相似度：高亮字符集合和原算法重合多少。
- 密度偏差：每段高亮比例是否接近原算法。

## 2026-06-03 长文无高亮故障修复

- 用户反馈：导入长文后页面完全没有高亮标注，状态条显示 `MiniMax response did not include text content.`。
- 已确认这不是 CSS 或 `mark` 渲染问题，而是 `/api/highlight` 失败导致页面没有任何 `HighlightMap` 可渲染。
- 复现结果：
  - 本地构造 37 段长文请求 `/api/highlight`，旧实现返回 HTTP 500。
  - 直连 MiniMax-M3 诊断显示：HTTP 200，但 `stop_reason=max_tokens`，`contentTypes=["thinking"]`，没有最终 `text` block。
  - 根因：长文整篇一次性请求时，M3 把 4096 输出 token 消耗在 thinking 上，没有来得及输出 JSON。
- 修复方式：
  - 将 MiniMax 高亮请求改为小批量处理：每批最多 4 段 / 1200 字符。
  - 批量请求最多 5 个并发。
  - 每批返回独立 `HighlightMap` 后在服务端合并。
  - 如果某一批仍然返回 thinking-only、非 JSON 或不可恢复结构，则自动二分该批次重试。
  - 前端长文状态改为显示：`生成语义高亮中... 正在分批处理 N 段，请保持页面打开。`
- 回归测试：
  - 新增“长文请求会分批并合并 HighlightMap”测试。
  - 新增“结构化输出失败后会拆小批次重试”测试。
  - `npm run test:web-mvp` 通过，26 tests, 26 pass, 0 fail。
